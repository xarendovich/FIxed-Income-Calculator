# Spark daemon pattern — r3 review findings (verification, bug hunt, hardening)

- **Status:** DRAFT FOR ADJUDICATION, companion to `README.md` (r3). Nothing here is a Class C ruling.
- **Revision:** r3, 2026-09-27, by Claude, reviewing the r2 package (`spark-daemon-pattern-v0.2.zip`) as received.
- **Method:** read every module; reproduce each suspected defect against the unmodified r2 code before changing anything; fix; add a regression test that fails on r2 and passes on r3; re-run the whole suite and the battery. A finding is listed only if it was reproduced (the "Reproduced on r2" column) or, for the two design-level items, measured.

## Summary

Baseline: r2's own 105 self-tests and 18 battery checks all passed on this workspace (Python 3.11, Landlock ABI 7). They did, but the review still found **22 defects** (plus one missing-evidence note, HF-23). Among them are two ways for daemon code to run or read what it must not (HF-01/02, HF-03), a unit that could never have started the daemon once installed (HF-07), a deployment shape in which every Git daemon silently observes nothing (HF-08), and a battery that passed a daemon failing on every cycle (HF-16). The layered design held. Landlock contained the file-system effects of every escape it could see, which is the strongest evidence the r2 design is sound. But each escape went through a layer that was supposed to stop it first.

Later work found fourteen more, each fixed with a test that fails on the revision before its fix (HF-32 was reproduced in r3.9 and fixed in r4.0). HF-28, HF-30 and HF-31 were found by reading or arithmetic (there is no systemd PID 1 here); the rest were reproduced by running: HF-24 (r3.1, a Git code-execution path the Observer had already closed), HF-25 and HF-26 (r3.2, from the WBS 3.1 final contract and the WBS 3.0 r4 closeout), HF-27 (r3.3, an evidence gap found while reviewing the plug-and-play proposal), HF-28 and HF-29 (r3.5, found while adding the blind period), HF-30 to HF-32 (r3.9, limits in conflict; HF-32 fixed in r4.0), HF-33 (r4.3, found by applying the LTC hardening markup's bounded-payload rule, LTC-H01), HF-34 and HF-35 (r4.5, found while adjudicating the r4.2 to r4.4 improvements), HF-36 (r4.6, found while checking a hardening recommendation's Landlock claims against the code), and HF-37 (r4.7, found by the first real deployment target).

After r3: 170 self-tests pass on Python 3.10, 3.11, 3.12 and 3.13 (105 original, 65 new), and all four reference daemons pass the battery 18/18. Evidence is in `evidence/r3/`.

## Residual risks (known, not fixed; for adjudication)

1. **Closed in contract 5 (R-2): no daemon runs Git.** *Was:* **Repository-owned Git config is still trusted (PD-25).** With `safe.directory` scoped to the declared repository, that repository's own `.git/config` applies. Pager, fsmonitor, external diff and textconv are neutralised, and hooks do not run for read-only commands. But a **filter driver** (`filter.<name>.clean`, selected by `.gitattributes`) can run during `git status`/`git diff` on worktree files. Landlock (read-only on the repo, write only to the output dir, no TCP) and the systemd unit contain it. Recommendation: accept for repositories the owner controls; refuse `status`/`diff` on worktrees you do not control (observe a bare mirror instead, as `git-watch`'s fixture does).
2. **Purity is still syntactic.** r3 closes every route found in review; it cannot prove none remain. The design already says so. What changed is that each known route is now a named rule in the contract and a test, and Landlock stays the backstop (DB-17 proves it acts alone).
3. **Still never run under real systemd.** The seccomp fix (HF-07) is derived from `systemd-analyze syscall-filter` group membership and checked by DB-15, but no unit has been started by PID 1. The first DGX step should install `meminfo-watch` as a unit and confirm `DAEMON_START.landlock.status == "enforced"`.
4. **Closed in contract 5 (R-2): `ctx.run` is gone.** *Was:* **`ctx.run` arguments are the manifest reviewer's responsibility.** The skeleton polices *which* command runs, not what its flags do. The denylist now covers the known command runners; anything else on a manifest's `commands` list deserves the same scrutiny as Git got here.
5. **The head of the chain is not anchored (PD-58, not built).** A hash chain proves that every record before its head is unchanged, and nothing more. The last record can be edited in place, or the ledger cut back to any earlier record, and both verifiers will still report an intact chain with a different head (the contract 5 verification fuzz shows it, `test_independent.DifferentialFuzzTests`). Only a head recorded outside the daemon's output directory (journald, another host) can show it. Until PD-58 is built, I-4's "verified two independent ways" means *relative to the head*. Recommendation: word I-4 to say so in contract 5.0.1, and decide PD-58. *2026-10-08: elevated from a residual to a prerequisite — no consumer treats an intact chain as complete until a head is anchored off the output directory; the first consumer attachment is the anchor (`ADJUDICATION-ALIGNMENT-REVIEW.md`, item 4).*
6. **What was judged does not include the skeleton itself (V-1).** A qualified unit pins the manifest, `daemon.py` and the contract *text*; it does not pin the code that enforces the contract (`spark_daemon/`, `verifier/`). A skeleton edited after qualification, for example with the audit hook stubbed out, still starts under the qualified unit, and the contract identity is unchanged (reproduced in `VERIFICATION-V5.md`, item 2). r4.11 had the same gap. Mitigation today: install the pattern root-owned and read-only (the install plan says so). Proposal for the owner: bind a skeleton tree digest (the vendoring tool's `tree_sha256` over `spark_daemon/` and `verifier/`) as a fourth expected digest. The 2026-10-08 class-requirements review names this **ADM-9**, the one admission requirement still open: until that digest exists a qualified unit does not prove the enforcer that will run. It is the 6.0.0 change (`ROADMAP.md` §2).
